# Подарочные сертификаты

## Согласованные правила

- Оплата через существующий PayKeeper; код отправляется только покупателю на email.
  По уточнению от 04.10.2026 Telegram-доставка отложена.
- Номиналы: 1000, 2000, 3000, 4000, 5000, 6000, 8000, 10000, 12000,
  14000, 16000, 18000, 20000 рублей.
- Уникальный код появляется только после подтверждённой сервером оплаты.
- Срок действия — один календарный год с момента подтверждения оплаты;
  для 29 февраля дата окончания — 28 февраля следующего года.
- Один сертификат на заказ. Он покрывает изделие вместе с вышивкой,
  но не доставку. Остаток сохраняется для последующих заказов;
  непокрытая сумма оплачивается через PayKeeper.
- Автоматического возврата потраченного баланса нет: отмены и возвраты
  разбираются вручную. Освобождение неоплаченного резерва не является возвратом.
- Статусы: «Ожидает оплаты», «Активен», «Использован», «Аннулирован».

## Итерация 1: серверный учёт

Реализованы три отдельные таблицы с версионируемыми миграциями:

- `gift_certificates`: покупатель, номинал, баланс, платёж, срок, защищённый код;
- `gift_certificate_reservations`: удержание части баланса под один заказ;
- `gift_certificate_operations`: журнал выдачи и подтверждённых списаний.

Существующие таблицы заказов не изменяются. Эта итерация подготовила учёт;
форма, платёжные API и доставка добавлены в итерации 2 ниже.
Применение сертификатов в оформлении и админка пока не подключены.

Все новые денежные поля хранят целые копейки. Сумму и режим покупки определяет
сервер, а не клиент. До оплаты баланс равен нулю. Активация, срок, защищённый
код и запись выдачи фиксируются одной транзакцией. Повтор того же платежа
не создаёт код заново, не продлевает срок и не пополняет баланс повторно.

Код содержит 128 бит случайности. Для поиска хранится SHA-256, а для повторной
доставки — копия, зашифрованная AES-256-GCM и привязанная к ID сертификата.
Нельзя включать код, хеш или зашифрованную копию в публичные ответы, админские
списки и логи. Внутренний метод доставки проверяет целостность и совпадение хеша.

Резерв не списывает деньги. Доступный остаток учитывает активные резервы
других заказов. Все изменения блокируют строки в одном порядке:
заказ → сертификат → резерв. Уникальность резерва по заказу запрещает применение
двух сертификатов. Подтверждённое списание и его запись в журнале атомарны;
повторное списание того же заказа ничего не меняет.

При позднем подтверждении платежа освободившийся резерв можно восстановить
только в прежней сумме и при достаточном доступном балансе. Если баланс уже
использован, сертификат истёк или аннулирован, нужна ручная проверка платежа.
Нельзя уменьшать уже оплаченный дисконт, повторно расходовать чужой резерв
или молча считать такой заказ успешно оплаченным.

Истечение срока определяется `getCertificateStatus` при проверке сертификата,
в том числе на точной границе срока. Сохранённый статус может оставаться
`active`: будущая админка должна показывать вычисленный статус, а не только
значение колонки. Обработчик освобождения старых резервов готов, но пока
не подключён к расписанию.

Тестовый сертификат сохраняет номинал и ожидаемую оплату 100 копеек.
Он несовместим с обычным режимом оформления. Подтверждение ранее созданного
тестового заказа использует сохранённый режим резерва, поэтому переключение
глобального флага не ломает уже выданный счёт. При запуске production тестовые
сертификаты не должны становиться обычными.

## Ключ шифрования

В `.env.production.example` добавлен `CERTIFICATE_CODE_ENCRYPTION_KEY`:
отдельный случайный ключ длиной 32 байта, записанный 64 шестнадцатеричными
символами. Реальные `.env` и сервер на этом этапе не менялись.

До включения покупки необходимо безопасно создать ключ, положить его в
серверный env и обеспечить отдельную защищённую резервную копию. Не присылать
его в переписку и не коммитить. Потеря ключа лишает возможности повторно
доставить существующие коды; простая замена ключа не является ротацией.
Без корректного ключа выдача кода прекращается с ошибкой, а транзакция
активации откатывается. Checkout проверяет готовность
шифрования и доставки **до** создания платёжного счёта.

## Проверки

```powershell
npm test
npm run lint
npm run test:migrations
```

Последняя команда создаёт отдельную временную БД
`its_migration_test_<pid>_<timestamp>` на настроенном PostgreSQL, применяет
миграции, проверяет серверный учёт, откатывает и повторно применяет миграции,
затем удаляет только эту временную БД. Учётной записи нужны права её создания.
Для локального запуска следует использовать локальный PostgreSQL,
не production-подключение.

Интеграционный сценарий проверяет повторные подтверждения, уникальность
платежа, ограничения SQL, конкурентное резервирование и списание,
частичное использование, освобождение резерва, запоздавшее подтверждение,
откат транзакции, истечение срока и разделение тестового/обычного режима.
Прямой запуск `verify-certificate-balances.js` вне такой тестовой БД запрещён.
Реальные PayKeeper, СДЭК, email и Telegram в этих проверках не вызываются.

## Итерация 2: покупка и доставка

Форма реализована по мобильному макету Figma `165:339`, на широких экранах
использует двухколоночный паттерн оформления заказа. Поля вынесены в общий
`RecipientPersonalFields`, маска телефона переиспользуется. Выбор доставки
и отдельного получателя отсутствует. Email обязателен, ФИО может состоять
из фамилии и имени. Изображения скачаны из Figma и оптимизированы в WebP.
На мобильном текст полей не меньше 16 px.

API:

- `GET /api/certificates/config`: номиналы, доступность покупки, тестовый режим,
  публичная Turnstile-конфигурация с action `certificate_purchase`;
- `POST /api/certificates/purchase`: строгий DTO, Origin-проверка, общий Redis
  rate limit и Turnstile; UUID v4 в `Idempotency-Key` обязателен;
- `POST /api/certificates/:id/payment`: только пустой JSON-объект, Origin,
  rate limit и `X-Certificate-Access-Token`; сумму задаёт сервер;
- `GET /api/certificates/:id/status`: тот же покупательский токен, без кода,
  хеша, зашифрованной копии и персональных данных покупателя.

Покупательский JWT живёт семь дней и имеет отдельные issuer/audience/purpose
и секрет. Он не заменяет админский или гостевой токен заказа. Ответы покупки
и статуса имеют `Cache-Control: no-store`. UUID запроса и отпечаток
нормализованных данных не позволяют сетевому повтору создать другую покупку.
Повтор с тем же UUID, но другими данными отклоняется.

PayKeeper получает `orderid=certificate-<id>`. Уже существующий подписанный
callback различает обычные заказы и сертификаты; перед активацией проверяет
подпись и сохранённую сумму. Параметр `paymentConfirmed` остаётся внутренним,
из пользовательского JSON не принимается.
Запрос счёта фиксируется до обращения к шлюзу. При потерянном ответе повтор
сначала ищет прежний счёт через API PayKeeper; не создаёт второй вслепую.
Неоднозначный результат требует проверки, не повторной оплаты.

Используются существующие страницы возврата `/payment-success` и
`/payment-fail`: локальный маркер вида платежа направляет покупателя на
`/certificate`. Доступ и данные покупки сохраняются только в sessionStorage,
не в URL. Перезагрузка продолжает проверку, но сама по себе не доказывает оплату.
В том же браузере переход к оплате обычного заказа заменяет маркер на `order`.

Подтверждение оплаты и запись в новой таблице `gift_certificate_deliveries`
атомарны. Callback не ждёт SMTP. Воркер каждую минуту забирает задания с
блокировками строк и lease на три минуты; другие процессы не отправляют
то же активное задание. После сбоя процесса просроченный lease восстанавливается.
При ошибке отправки — экспоненциальные повторы, максимум 12 попыток.
Код при повторах неизменен; повтор callback не сбрасывает backoff и не
отправляет уже отправленное письмо ещё раз.

SMTP не может гарантировать exactly-once: если письмо принято, а процесс
упал до отметки в БД, возможен повтор того же письма. Message-ID постоянный,
новый код при этом не выдаётся. Статус `sent` означает принятие письма SMTP,
не гарантированное попадание во входящие. После исчерпания попыток статус
`failed`, ошибка видна мониторингу; нужна ручная проверка и повторная отправка.
Логи содержат только ID покупки, номер попытки и безопасный код ошибки.
Коды сертификатов не отправляются сотрудникам или Telegram-подписчикам.

### Настройка email позже

По согласованию SMTP-аккаунта пока нет. Настройки подготовлены только в
`.env.production.example`; реальные env и сервер не изменялись:

```text
CERTIFICATE_PURCHASE_ENABLED=0
CERTIFICATE_CODE_ENCRYPTION_KEY=
CERTIFICATE_ACCESS_SECRET=
CERTIFICATE_SMTP_HOST=
CERTIFICATE_SMTP_PORT=465
CERTIFICATE_SMTP_USER=
CERTIFICATE_SMTP_PASSWORD=
CERTIFICATE_MAIL_FROM=
```

Ключ и секрет — разные случайные значения по 64 hex-символа, отдельные от
админского JWT и гостевого доступа. `CERTIFICATE_MAIL_FROM` — один email,
без списка адресов и отображаемого имени. SMTP использует TLS на 465 или
обязательный STARTTLS на 587; проверка сертификата TLS не отключается.
Checkout проверяет SMTP-соединение и авторизацию до запроса платёжного счёта.
Если настройки отсутствуют, API отклоняет покупку, но форму можно просматривать.
При включённом флаге некорректная конфигурация блокирует запуск приложения.
Отключение новых покупок не останавливает доставку уже оплаченных сертификатов.

Позже выбрать почтового провайдера, подтвердить адрес отправителя, настроить
SPF/DKIM и проверить реальное письмо на стенде. После завершения применения
сертификатов в итерации 3 можно включать покупки. Для production отключить
рублёвый тестовый режим. Сейчас реальные платежи и письма не проверялись:
интеграционные проверки используют заменённые адаптеры в отдельной временной БД.

## Следующая итерация: применение и админка

- Поле кода на последнем шаге, расчёт непокрытой суммы только на сервере.
- Резерв баланса в одной транзакции с созданием заказа и резервом остатков;
  срок согласован с резервом товара. Подключить освобождение старых резервов.
- Зафиксировать скидку, доставку и непокрытую сумму до создания счёта.
  После выдачи счёта их нельзя менять.
- Списание сертификата в одной транзакции с подтверждением оплаты заказа.
  Полностью покрытый заказ без платной доставки требует отдельного серверного
  завершения без фиктивного банковского платежа.
- Ручная проверка запоздавших платежей при недоступном балансе; без
  автоматического возврата и без пометки проблемного заказа как успешного.
- Защищённая админка: покупатель, номинал, доступный/удержанный баланс,
  срок, вычисленный статус и история операций, без раскрытия кода в списке.
- Браузерные тесты покупки, доплаты, полного покрытия, повторного применения
  остатка и ошибок кода.

Корзина и несколько изделий в одном оформлении — отдельная работа;
кнопка «Добавить в корзину» не включается без согласованного механизма корзины.
